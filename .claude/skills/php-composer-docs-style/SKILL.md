# Стайлгайд документации PHP-инструмента (VitePress)

Правила оформления документации для opensource-инструмента на PHP, который
распространяется через Composer. Важно: документация обычно описывает **инструмент
целиком**, а не один пакет — инструмент часто состоит из нескольких Composer-пакетов
(например `vendor/kafka-bus-core`, `vendor/kafka-bus-consumer`, `vendor/kafka-bus-cli`),
и документация должна показывать его как единый продукт: с описанием возможностей,
быстрым стартом, гайдами по сценариям использования, и уже внутри — по отдельным
пакетам, если это нужно читателю. Стек документации: VitePress + Markdown.

Используй этот файл как основной источник правил. Для детальных правил PSR-12
(конкретные примеры кода, форматирование классов/методов) смотри
`references/php-code-style.md` — открывай его, когда пишешь или проверяешь
PHP-код внутри примеров документации.

## 1. Архитектура документации (Diátaxis)

Перед тем как писать конкретную страницу, определи её тип — смешивание типов
внутри одной страницы главная причина мутной документации.

- **Tutorial** — обучающий урок для новичка, шаг за шагом, гарантированный результат.
  Пример: «Быстрый старт: установка и первый запрос».
- **How-to guide** — рецепт решения конкретной задачи, читатель уже знает основы.
  Пример: «Как подключить кастомный HTTP-клиент», «Как настроить кэширование».
- **Reference** — сухие факты: методы, параметры, типы, исключения, конфигурация.
  Не читают целиком, а ищут конкретную деталь. Для PHP-пакета это в первую очередь
  описание публичного API (классы, интерфейсы, методы).
- **Explanation** — контекст и «почему»: архитектурные решения, компромиссы,
  сравнение с альтернативами.

Правило: в tutorial не объясняй "почему" подробно — одна строка + ссылка на
explanation-страницу. В reference не должно быть пошаговых инструкций. В how-to
не нужно учить теории — только шаги к результату.

## 2. Информационная архитектура: инструмент, а не пакет

Не проектируй документацию вокруг структуры репозитория/пакетов Composer —
проектируй её вокруг задач читателя. Пакеты — это детали реализации, о которых
читатель узнаёт по мере погружения, а не с первой страницы.

Используй модель **hub-and-spoke**: центральная страница (хаб) знакомит с
инструментом целиком и ссылается на самостоятельные разделы («spokes»), каждый
из которых закрывает свою тему и может при необходимости содержать отдельные
инструкции по установке нужных пакетов.

**Обязательные верхнеуровневые разделы для документации инструмента:**

1. **Overview / Главная страница** — что за инструмент, какую проблему решает,
   для кого. Не техническая деталь, а питч в 3–5 предложений.
2. **Возможности (Features)** — список ключевых фич инструмента, каждая с
   коротким описанием (1–2 предложения) и ссылкой на подробный гайд/reference.
   Оформляй как сетку карточек или маркированный список с заголовками-фичами,
   не как сплошной текст.
3. **Быстрый старт (Quickstart / «Запуск за 5 минут»)** — минимальный путь от
   `composer require` до работающего примера. Использует один вход (например,
   мета-пакет или CLI), не заставляет читателя решать, какие из 5 пакетов ставить.
4. **Установка и требования** — полная матрица: какие пакеты за что отвечают,
   какие ставить в каких сценариях (например: «нужен только продюсер сообщений —
   ставьте `vendor/kafka-bus-core` и `vendor/kafka-bus-producer`»).
5. **Гайды (How-to)** — сценарии использования, которые могут затрагивать
   несколько пакетов сразу (не дели гайд по границам пакета, если задача читателя
   этого не требует).
6. **Reference по компонентам/пакетам** — здесь уже уместно разбиение по пакетам:
   у каждого пакета — свой раздел reference (`## Пакет kafka-bus-consumer`),
   если у инструмента много пакетов с разным API.
7. **Concepts / Explanation** — архитектура, как компоненты инструмента
   взаимодействуют между собой (например: как producer и consumer используют
   общий core-пакет).

Общие (cross-cutting) темы — конфигурация, обработка ошибок, логирование,
трейсинг — выносятся в отдельные страницы, а не дублируются в доке каждого
пакета. Ссылайся на них из reference-страниц пакетов.

Список пакетов и их назначение стоит показывать таблицей на странице
установки/архитектуры:

| Пакет | Назначение | Обязателен |
|---|---|---|
| `vendor/kafka-bus-core` | Общие контракты и сериализация | Да |
| `vendor/kafka-bus-producer` | Отправка сообщений | Опционально |
| `vendor/kafka-bus-consumer` | Чтение и обработка сообщений | Опционально |

## 3. Заголовки страниц и разделов

- Один `#` (H1) на страницу — заголовок документа. Дальше только `##` и глубже,
  без перескока уровней.
- Sentence case («Установка через Composer», а не «Установка Через Composer»),
  без точки в конце.
- Заголовок описывает задачу/тему с точки зрения читателя: `## Настройка через переменные окружения`,
  а не `## Env`.
- **Не используй в заголовках имена PHP-классов/методов и спецсимволы**
  (`::`, `->`, `()`, `$`, `\`, обратные кавычки). Такие заголовки плохо читаются,
  ломают автогенерируемые якоря VitePress (`#configmergeconfigconfig` вместо
  человекочитаемого `#slug`) и не подходят человеку, который ещё не знает API.
  Опиши заголовок по-человечески, а сигнатуру покажи ниже, в теле раздела
  (как код или как подзаголовок):

  ```markdown
  <!-- Плохо -->
  ## `CacheManager::get()`
  ## $config->set('driver', 'redis')
  ## Provider\Cache\RedisProvider

  <!-- Хорошо -->
  ## Получение значения из кэша

  Метод `get()` класса `CacheManager` возвращает значение по ключу.
  ```

  Исключение — reference-страницы, сгенерированные автоматически из докблоков
  специализированным генератором (не вручную), если инструмент генерации сам
  строит корректные якоря; ручные Markdown-страницы этому правилу следуют всегда.

## 4. Структура страницы

```markdown
# Заголовок страницы

Один-два абзаца: что это, зачем нужно, для кого. Не веди себя так,
будто читатель уже знает контекст инструмента.

## Первый раздел
Содержимое.

## Второй раздел
Содержимое.
```

Вводный абзац обязателен всегда. VitePress сам строит TOC из заголовков —
не дублируй оглавление вручную.

## 5. Установка, версионирование и README

- **Установка.** На странице установки/quickstart всегда показывай самый частый
  сценарий первым — например, мета-пакет или CLI-инструмент, если он есть:
  ```bash
  composer require vendor/kafka-bus
  ```
  Отдельные пакеты (`vendor/kafka-bus-consumer` и т.д.) показывай ниже, в блоке
  «Установка отдельных компонентов», с пояснением, когда какой нужен. Не начинай
  страницу установки с перечисления всех пакетов подряд — это перекладывает
  выбор на читателя раньше, чем он готов его сделать.
- **Требования (Requirements).** Явно укажи минимальную версию PHP и обязательные
  расширения (`ext-json`, `ext-mbstring` и т.д.). Если у разных пакетов инструмента
  разные требования (например, consumer требует `ext-rdkafka`, а core — нет) —
  укажи это в таблице пакетов, а не общей строкой.
- **Автозагрузка.** Если пакет не подключается автоматически через Composer
  autoload, покажи пример `use Vendor\Package\ClassName;`.
- **Версионирование.** Указывай, для какой major-версии инструмента написана
  документация (SemVer). Если пакеты инструмента версионируются независимо друг
  от друга — явно поясни это и покажи таблицу совместимости версий пакетов между
  собой. Breaking changes — отдельная страница миграции, а не сноски внутри reference.
- **README.md** (как корневого репозитория/инструмента, так и README отдельных
  пакетов, если они лежат в разных репозиториях):
  1. Бейджи (версия на Packagist, поддерживаемые версии PHP, лицензия, статус CI).
  2. Одно предложение — что делает инструмент.
  3. Короткий список ключевых возможностей (3–6 пунктов).
  4. Установка.
  5. Минимальный пример использования (Quick Example) — самый частый сценарий,
     решаемый в 5–10 строк кода.
  6. Ссылка на полную документацию (VitePress-сайт) — README не должен пытаться
     заменить полную документацию.
- **CHANGELOG.md** — по формату Keep a Changelog (`## [1.2.0] - 2026-08-01`,
  секции `Added` / `Changed` / `Fixed` / `Removed`). Если пакеты версионируются
  раздельно — у каждого пакета свой CHANGELOG; на верхнеуровневой странице релизов
  инструмента давай сводку, что изменилось во всех пакетах разом.

## 6. Примеры кода

- Всегда указывай язык у код-блока: ` ```php `, ` ```bash `, ` ```json ` (для
  `composer.json`) — без языка Shiki не подсветит синтаксис.
- Один блок = одна логическая единица. Не склеивай установку, конфиг и запуск
  без разделения на отдельные блоки.
- Пропуски в коде — комментарием `// ...`, не многоточием `…` как символом.
- Код должен быть рабочим и копируемым as-is. Если что-то нужно заменить
  (`YOUR_API_KEY`), явно поясни это рядом с блоком.
- Каждый нетривиальный пример показывает и вход, и результат (что вернёт метод,
  что попадёт в лог) — если это не очевидно из кода.
- PHP-примеры в документации должны соответствовать PSR-12 — см.
  `references/php-code-style.md`.

### VitePress-специфика для кода

**Подсветка строк:**
````markdown
```php{2,4-5}
function setup(): void {
    $a = 1;
    $b = 2;
    $c = 3;
}
```
````

**Группы кода** (например, разные способы установки/конфигурации):
````markdown
::: code-group
```bash [Composer]
composer require vendor/package
```
```json [composer.json]
{
    "require": {
        "vendor/package": "^2.0"
    }
}
```
:::
````

**Diff внутри блока** (например, при показе миграции между версиями):
````markdown
```php
$client = new Client(); // [!code --]
$client = Client::create($config); // [!code ++]
```
````

## 7. Admonition-блоки (врезки)

Не пиши «Важно:» жирным текстом внутри абзаца — используй встроенные контейнеры
VitePress, они визуально единообразны по всей документации.

```markdown
::: tip
Необязательный совет.
:::

::: warning
Что-то может пойти не так, если это проигнорировать.
:::

::: danger
Разрушительное или необратимое действие (например, `DROP TABLE` в примере миграции).
:::
```

Уровни по смыслу:
- `tip` — необязательная рекомендация.
- `[!IMPORTANT]`/`::: info` — факт, который легко пропустить.
- `warning` — риск, требующий внимания сейчас (например, breaking change).
- `danger` — необратимые последствия (потеря данных, деплой в прод).

Выбери один синтаксис (либо `::: type`, либо GitHub-style `> [!NOTE]`) как
стандарт проекта и не смешивай оба.

## 8. Списки, ссылки, термины

- Нумерованный список — только когда порядок шагов важен, иначе маркированный.
- Текст ссылки описывает, куда она ведёт («см. руководство по конфигурации»),
  не «нажмите сюда».
- Внутренние ссылки — относительные пути к `.md`-файлам, VitePress сам
  конвертирует их в SPA-роутинг.
- Единый словарь терминов инструмента (как называется сущность — «провайдер»,
  «контракт», «фабрика» и т.д.) — используй одни и те же термины во всех
  пакетах и разделах, не чередуй синонимы.

## 9. Тон и стиль текста

- Обращение на «вы», активный залог: «метод возвращает объект», а не
  «объект возвращается методом».
- Короткие предложения, один тезис на предложение.
- Императив в инструкциях: «Установите пакет», а не «Вам нужно будет установить».
- Настоящее время для описания поведения: «команда создаёт файл», а не
  «команда создаст файл».

## 10. Таблицы

- Таблицы — для параметров/опций/сравнений, не для длинных текстовых описаний.
- Для описания параметров метода: `Параметр | Тип | По умолчанию | Описание`.
- Не больше 4–5 колонок — на мобильном таблица обрежется.

## 11. Frontmatter страницы (VitePress)

```yaml
---
title: Настройка провайдера кэша
description: Как подключить и настроить провайдер кэша в пакете
---
```

`title` и `description` — обязательны на каждой странице (SEO и превью в соцсетях).

## 12. Чек-лист перед публикацией страницы

- [ ] Один H1, заголовки без пропуска уровней
- [ ] В заголовках нет имён PHP-классов/методов и спецсимволов (`::`, `->`, `()`, `$`, `\`, обратных кавычек)
- [ ] Есть вводный абзац
- [ ] Страница не заставляет читателя с порога выбирать между пакетами инструмента —
      выбор пакета отложен до раздела установки/reference
- [ ] У всех код-блоков указан язык, PHP-примеры соответствуют PSR-12
- [ ] Установка показана через `composer require`, версия PHP и расширения указаны явно
- [ ] Важные предупреждения — через `::: warning`/`::: danger`, не жирным текстом
- [ ] Ссылки с осмысленным текстом
- [ ] Термины совпадают со словарём проекта (единые для всего инструмента, а не по пакету)
- [ ] Страница явно относится к одному типу Diátaxis (tutorial/how-to/reference/explanation)
